# 設計: MVP スコープと技術方針

戦略・背景・決定記録(D1–D10)は [concept.md](concept.md) を参照。
本ファイルは「どう作るか」(MVP の範囲と技術構成)を扱う。

## 1. MVP スコープ

### 入口

条件検索。絞り込み軸は 3〜5 個の少数精鋭で始める(軸が多いほど 1 件あたりの
調査コストと実装が膨らむため)。

### 画面構成(最小)

1. 検索ページ(絞り込み + 一覧)
2. キャンプ場詳細ページ(スペック表 + 地図)

### 体験原則

モバイルで軽く速く使えること(D9)。ただしモバイル操作性は差別化の主軸ではなく
**衛生要因**: 操作性への不満は小さく、本丸の不満は予約の取りにくさ・情報の
鮮度・信頼。既存大手(なっぷ/hinata/sotoshiru)も使いやすいアプリを持つため
**"使いやすさ"では戦わない**。UX は「他にない軸(程度・実測・中立)で絞り込める
× サッと使える」のセットで入口の取っかかりにとどめる(技術は下記 2)。

### やらないこと(MVP では)

- 予約機能・料金比較
- 自由記述レビュー(比較を壊す断片が増えるため恒久的にやらない)
- ユーザー投稿インフラ(認証・フォーム・モデレーション)。無人の初期は
  無意味なため MVP では作らない。ただし構造化 UGC を後段で開けるよう、
  データモデルには最初から投稿を載せられる余地を残す(D7 / concept.md
  「データ戦略」)
- レコメンド、横並び比較 UI
- 全国網羅

## 2. 技術方針

| レイヤ | 選定 | 状態 |
|---|---|---|
| フロントエンド | Next.js (App Router)。SEO 重視 + **PWA(モバイルファースト。ネイティブアプリは作らない)** | 候補 |
| バックエンド | Ruby on Rails API | 候補 |
| DB | PostgreSQL + PostGIS | 候補 |
| 地図 | MapLibre + OpenStreetMap(Google Maps 非依存) | 候補 |
| ストレージ | S3 互換(Cloudflare R2) | 候補 |
| インフラ | Vercel / Fly.io / Supabase | 候補 |

方針: **PWA + Web** を主軸とする(D9)。ネイティブアプリは作らない。理由:
(1) なっぷ・hinata・sotoshiru が既にネイティブアプリを保有し概ね好評＝
アプリ空白は無い、(2) 操作性は衛生要因で差別化にならない、(3) ネイティブは
SEO(広告収益の生命線)に乗らない。Web は SEO とモバイル体験を両立でき、
PWA でホーム画面追加・オフライン閲覧などアプリ的な使い勝手も足せる。

実装開始時に ADR として確定させる。
