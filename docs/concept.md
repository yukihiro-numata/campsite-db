# コンセプトドキュメント

最終更新: 2026-07-11

## 1. 目的

趣味で長く育てられる Web サービスを個人開発する。

- 個人開発として継続できる規模で運営する
- 新しい技術を学びながら開発する
- GitHub で公開し、ポートフォリオとして通用する品質を目指す

AI を前提とした**プロダクト**にはしない(チャットで「おすすめを教えて」
のような AI 表面は作らない)。プロダクトの芯は構造化検索・地図・比較。
プロダクト設計・検索・地図・データモデリング・インフラを重視する。

ただし **AI を「データ収集の裏方ツール」として使うことは前提と矛盾しない**。
web 上に散在する実地情報をクロール・抽出して DB を埋める用途は、
プロダクト表面ではなくビルド時の道具であり、上記方針の範囲内とする(6 節)。

## 2. 課題仮説(競合・ペイン調査で検証済み / 2026-07-11)

### 修正後の仮説(確定)

キャンプ初心者が本当に比較したい「行ってみないと分からない情報」のうち、
**"有無・種類"レベルは既存サービスで構造化されつつある。空白なのは
"程度・定性・実測"の情報**(地面の硬さ、トイレのきれいさ、混雑度の実測、
静かさの度合い、サイトの実寸、所要時間での絞り込み)である。これらは
ブログ・YouTube・口コミに散在し、横断比較できない。

→ **"行ってみないと分からない程度・実測情報"を比較可能な軸に構造化**
できれば差別化できる。当初の「スペックが無いから作る」は誤りで、
「散在する質的情報を構造化・横断比較可能にする」に芯を修正した。

### 検証サマリ

当初仮説を A/B/C に分解して検証した(手法: 競合ライブ調査 + Web上の
ペイン調査)。

| 主張 | 判定 | 要点 |
|---|---|---|
| A. 既存は予約・口コミ中心でスペック非構造化 | **半分は誤り** | hinata スポットが地面の種類・24時間管理・近隣コンビニ/スーパー・車乗り入れ・穴場までタグ構造化し掛け合わせ絞込も可能。ただし予約主軸のなっぷは薄く、TAKIBI は予約撤退(2024/9末) |
| B. 実地情報がブログ・YouTube に散在 | **限定的に成立** | 「有無・種類」は構造化済み。散在するのは「程度・定性・実測」情報 |
| C. 初心者の痛みが実在し情報探しに時間がかかる | **概ね成立(中〜強)** | 地面・騒音・トイレ・広さ・買い出しで失敗談/回避策が多層的に存在。「ブログ/YouTube を漁る」が選び方の王道として指南され、集約する二次サービスまで出現 |

### 競合の構造化状況

| サービス | 主目的 | 構造化済み(=差別化にならない) |
|---|---|---|
| なっぷ | 予約 + 検索(最大級) | エリア/料金/予約可否/サイトタイプ/電源/風呂/ペット/様式トイレ。サイト広さは「100㎡以上」の二値特集どまり |
| hinata スポット | 検索(メディア起点) | 上記に加え **地面の種類/24時間管理/近隣コンビニ・スーパー/車乗り入れ/穴場** までタグ構造化 |
| TAKIBI | 情報メディアのみ(予約は 2024/9 終了) | 予約・検索の競合としては実質消滅 |
| Google マップ | 地図 + 口コミ | 実地スペックは非構造化。ユーザーが口コミ件数から混雑度を自力推定 |

### 空白地帯(どこにも構造化されていない = 差別化余地)

1. 地面の"質"(ペグの刺さりやすさ・硬さ・水はけ) ※種類は hinata が構造化済
2. サイトの実寸(㎡)での範囲検索
3. トイレの"きれいさ"(様式は構造化済だが清潔感はない)
4. 混雑度の実測(時期別・実データ)
5. 静かさの"度合い"(穴場の二値のみ)
6. 都心/主要都市からの所要時間での絞り込み

### 判定

**Pivot ではなく「仮説を修正して Go」。** 課題は実在するが、差別化の芯は
「スペックが無い」ではなく「程度・実測情報が構造化されていない」に修正。
ただし後述の最大リスク(11 節)を直視することが Go の条件。

- hinata スポット: https://camp-spot.hinata.me/ (タグ例: /tags/gravel, /tags/always_management, /tags/convenience_store)
- TAKIBI 予約終了告知: https://www.takibi-reservation.style/media/news/138104
- 集約サービス(機会/競合シグナル): https://wom-camp.net/ , https://camp.toilet-now.com/ , https://campismfield.jp/review/
- ペインの声(例): Yahoo!知恵袋・BE-PAL 騒音特集 https://www.bepal.net/archives/283642 ・トイレ事前確認 https://nomad-r.jp/magazine/camping-ground-toilet/

## 4. MVP スコープ(案)

### 入口

条件検索。絞り込み軸は 3〜5 個の少数精鋭で始める(軸が多いほど
1 件あたりの調査コストと実装が膨らむため)。

### 画面構成(最小)

1. 検索ページ(絞り込み + 一覧)
2. キャンプ場詳細ページ(スペック表 + 地図)

### やらないこと(MVP では)

- 予約機能・料金比較
- 自由記述レビュー(比較を壊す断片が増えるため恒久的にやらない)
- ユーザー投稿インフラ(認証・フォーム・モデレーション)。無人の初期は
  無意味なため MVP では作らない。ただし構造化 UGC を後段で開けるよう、
  データモデルには最初から投稿を載せられる余地を残す(D7 / 6 節)
- レコメンド、横並び比較 UI
- 全国網羅

## 5. 絞り込み軸(提案・未決定)

初心者ターゲットのため「安心系」を主軸に、競合にない「差別化軸」を
1〜2 個混ぜる構成を提案する。

| 分類 | 候補 | 備考 |
|---|---|---|
| 安心系(主軸) | トイレのきれいさ / 売店・レンタル有無 / 管理人常駐 / 近隣の風呂・コンビニ | 初心者の最重要関心事 |
| 差別化軸(1〜2 個) | 車横付け可否 / 地面の種類(ペグの刺さりやすさ) / 静かさ | 競合が構造化していない情報 |
| アクセス系 | 都心からの所要時間 | 検索条件として汎用性が高い |

→ データ収集フォーマット作成時に確定する。

## 6. データ戦略

差別化の芯である「程度・定性・実測」情報(地面の硬さ・トイレのきれいさ・
静かさ・混雑度)は、1 人の手動収集では埋めにくい。これを **AI シード →
構造化 UGC で補完** の 3 層で解く。

### 3 層構造

1. **AI シード層**: web 上に散在する情報をクロール+抽出し、DB を"下書き"で
   埋める。クロール可能な軸(所要時間・地面の種類・トイレ様式・実寸)は
   一気に、主観軸(きれいさ・静かさ・混雑)も"暫定値+出典"で埋める。
   → 空欄を減らし、次段の投稿ハードルを下げる
2. **ユーザー確認・修正層(後段)**: 訪問者が「合ってる/違う」をワンタップで
   補正。0 からの空欄記入ではなく確認・修正にすることで投稿が集まりやすく、
   主観軸を実体験で上書きして鮮度・実測を担保する
3. **集約・モデレーション層**: 複数報告を集約(平均化)、出典・確認日・報告
   件数を保持。スパム/荒らしへの簡易対策

### 軸ごとの収集難易度(2 節の空白地帯より)

| 収集しやすさ | 軸 | 主な担い手 |
|---|---|---|
| 易(機械的) | 所要時間 | AI/地図 API |
| 中(公式・ブログにあれば) | サイト実寸・地面の種類・トイレ様式 | AI シード |
| 難(主観・鮮度) | トイレのきれいさ・静かさの度合い・混雑度の実測 | AI 暫定 → UGC で上書き |

無名サイト(web 上に情報が乏しく訪問者も少ない)は AI・UGC どちらでも
埋まりにくい。ここは自分の補正 or 実地訪問でカバーし、UGC は"更新・補完"
担当と割り切る。

### 原則

- **出典と確認日を項目ごとに記録**し鮮度を担保。各項目は出典種別
  (キュレーション/AI/ユーザー)・確認日・報告件数を持てるデータモデルにする
- **seed then crowdsource**: 投稿インフラはコールドスタート下では無意味。
  初期 30〜50 件は自分で埋め切って「エリア最強」を作り、価値と流入を
  作ってから投稿を開く(D7 / 4 節)
- 蓄積された「構造化された実測 UGC」は競合(hinata でもレビューしか無い)が
  持たない、時間が効く本当のモートになる
- 情報源: 公式サイト、自治体・観光情報、ブログ・SNS・YouTube、衛星写真、
  実地訪問、および将来のユーザー投稿

### 法務・信頼性の留意

- クロールは事実の集約に留め、他者コンテンツの丸ごと転載は避ける
  (robots/ToS・著作権に配慮)
- LLM 抽出は誤帰属・捏造がありうるため、必ず項目ごとに出典 URL を紐づけ、
  検証可能にする
