# コンセプトドキュメント

## 1. 目的

### 主目的

既存サービスでは不十分な点やできないことを補い、キャンプ場を簡単かつ便利に
探せるようにする。

### 副目的

1. **ポートフォリオとして公開する。** あわせて、少ない手間で持続的に開発できる
   構成を目指す。
2. **使いやすく、モダンなデザインにする。** 既存サービスの UI/UX に感じている
   使いづらさを解消する。

## 2. 課題仮説

### 仮説

キャンパーが比較したい「行ってみないと分からない情報」は、既存サービスでの
扱われ方で 2 つに分かれる。

- **有るか・どんな種類か(以下「有無・種類」)**: 例: トイレは有るか/水洗か、
  地面は砂利か芝か、オートサイトか、近くにコンビニがあるか。Yes/No や
  カテゴリで表せるため、hinata などが既にタグ化している。
- **どれくらいか(以下「程度・実測」)**: 例: トイレのきれいさ、地面の硬さ
  (ペグの刺さりやすさ)、静かさ、混み具合、区画の広さ(㎡)。量や度合いの情報で、
  ブログ・YouTube・口コミに散らばって横断比較できない。ここが空白。

→ この**「程度・実測」を比較できる軸に構造化**すれば、行く前に比べて選べるように
なり、キャンプ場探しが楽になる。

### 根拠1: 既存サービスは「有無・種類」止まり

| サービス | 主な用途 | 構造化済みの情報 |
|---|---|---|
| なっぷ | 予約 + 検索(最大級) | エリア/料金/予約可否/サイトタイプ/電源/風呂/ペット/様式トイレ。サイト広さは「100㎡以上」の二値どまり |
| hinata スポット | 検索(メディア起点) | 上記に加え **地面の種類/24時間管理/近隣コンビニ・スーパー/車乗り入れ/穴場** までタグ構造化 |
| TAKIBI | 情報メディアのみ(予約は 2024/9 終了) | 予約・検索サービスとしては実質終了 |
| Google マップ | 地図 + 口コミ | 実地スペックは非構造化。ユーザーが口コミ件数から混雑度を自力推定 |
| ソトシル | 記事のまとめ + 写真投稿 | 絞り込みは価格・施設タイプ・設備の有無・アクティビティ・周辺施設まで |

最も進んだ hinata でも「有無・種類」のタグ止まりで、「程度・実測」を軸に持つ
サービスは無い。

### 根拠2: ペインは実在

地面・騒音・トイレ・広さ・買い出しで失敗談や回避策が数多く見つかる。
「ブログや YouTube を調べる」が選び方の定番として紹介され、それを集約する二次
サービス(トイレ専用 DB・動画レビュー等)まで生まれている。

### 空白地帯(どの既存サービスも構造化していない情報)

1. 地面の"質"(ペグの刺さりやすさ・硬さ・水はけ) ※種類は hinata が構造化済
2. サイトの実寸(㎡)での範囲検索
3. トイレの"きれいさ"(様式は構造化済だが清潔感はない)
4. 混雑度の実測(時期別・実データ)
5. 静かさの"度合い"(穴場の二値のみ)
6. 都心/主要都市からの所要時間での絞り込み

## 2.5 既存サービスから学ぶこと

既存の集約サービスが「決定版」になれていない理由から、設計の方針を引き出す。

| 既存サービスでの問題 | 方針 |
|---|---|
| 1 つの軸だけ(トイレだけ・動画だけ)では候補を絞れない | 複数の軸で横断比較できるようにする |
| 他人のブログへのリンク集では価値が薄い | 自分でデータを持つ |
| 情報はすぐ古くなる(トイレ・地面・電波は変わりやすい) | 各データに最終確認日を持ち、鮮度を保つ |
| 件数が少ないと「載っていない」が増え、使われない | エリアを絞り、その中はもれなく載せる |
| 主観の星評価だけでは比べにくい | 決まった手順で測った実測値で持つ |
| 良い点しか分からない | 悪い点も含めて比べられるようにする |

## 3. 決定事項

実装・技術の判断は mvp.md / tech.md、収集や絞り込み軸の詳細は 4〜5 節に置く。
ここには方針レベルの決定だけを残す。

| # | 決定 | 内容 |
|---|---|---|
| D1 | ターゲット | キャンプ初心者〜中級者。自分自身をユーザーと想定 |
| D2 | MVP の型 | 条件検索 + 詳細ページから始める。予約・レビュー・レコメンドは作らない(詳細 mvp.md) |
| D3 | データの基点 | 自分の手作業での収集を基点とする(詳細 5 節) |
| D4 | 初期収録範囲 | 自宅周辺エリア 30〜50 件。まず「このエリアなら一番詳しい」状態を作る |
| D5 | リポジトリ | ドキュメント先行で最小構成から開始。モノレポ化は実装開始時 |
| D6 | 補完方針 | 構造化 UGC で補完(自由記述レビューではなく比較可能な軸への投稿・修正)。ただし初期は自分で埋め切ってから、後の段階でユーザー投稿を開く(5 節) |
| D7 | 提供価値 | 「程度・実測」を横断比較できる DB(2 節) |

## 4. 収集項目と絞り込み軸

**「収集項目」と「絞り込み軸」は別物**。収集項目は各キャンプ場について DB に
持つ全情報で広い。絞り込み軸(4.2)はそのうち検索で絞れるようにする少数精鋭で
狭い。例: 住所や料金は「収集するが絞り込み軸にはしない(詳細ページに表示する
だけ)」。両者を混同すると「絞り込み軸=集める情報の全部」と誤解する。

### 4.1 収集項目(各キャンプ場について DB に持つ情報)

既存サービスで探せない情報(下表③)だけでなく、**名称・住所などの当たり前品質(①)も
必須**。収集項目は 4 カテゴリに分ける。

| カテゴリ | 例 | 位置づけ |
|---|---|---|
| ① 基本情報(当たり前品質・必須) | 名称 / 住所 / 緯度経度 / 電話 / 公式URL / 営業期間・シーズン / 定休日 / IN・OUT 時刻 / **予約要否・予約方法** / 料金レンジ | **MVP 必須**。地図・詳細ページの土台 |
| ② 設備・サービス(有無中心) | サイトタイプ(区画/フリー/オート/コテージ) / AC 電源 / 風呂・シャワー・温泉 / 売店・レンタル / ゴミ捨て / **ペット可** / **直火・川遊び可否** / トイレ様式 / 近隣コンビニ・スーパー・風呂 | 既存サービスでも探せるが、"当たり前品質"として必要 |
| ③ 程度・実測(ペインの空白地帯) | 地面の質(硬さ・水はけ) / サイト実寸㎡ / トイレのきれいさ / 静かさの度合い / 混雑度 / 車横付け / 都心からの所要時間 | 2 節の空白地帯。サービスの中心 |
| ④ メタ情報(各項目に付随) | 出典種別(自分/AI/ユーザー) / 出典URL / 確認日 / **裏取り本数** / 確信度 | 鮮度・信頼性の担保 |

各カテゴリの「埋まりやすさ」は大きく異なる(5 節)。運用ルール:

- **緯度経度は「収集」でなく住所からの自動生成(ジオコーディング)**列に分類。
- **実測値は web からは取れない**ため、現地で確認したときだけ入れる。
- 品質は「埋まっている項目の割合」ではなく **「何件の情報源で確認できたか」**で
  測る(ブログ 1 本でも項目は埋まってしまうため)。

### 4.2 絞り込み軸(②③ から選抜した 5 軸)

「ターゲット(初心者〜中級者)に役立つ × 既存サービスで探せない × データを集められる」で 5 軸を選抜。

| # | 軸 | 分類 | 集め方 |
|---|---|---|---|
| 1 | 都心からの所要時間 | アクセス | AI/地図(易) |
| 2 | 車横付け(オートサイト)可否 | 安心・有無 | AI(易) |
| 3 | トイレのきれいさ | 程度・実測 | **web=参考 / 現地=確定** |
| 4 | 地面の種類 + 硬さ(ペグ) | 程度・実測 | 種類=AI / 硬さは **web=参考 / 現地=確定** |
| 5 | 静かさ・混雑(穴場度) | 程度・実測 | UGC/AI 暫定 |

- 売店・レンタル・風呂・近隣コンビニ等は**収集はするが絞り込み軸にはしない**
  (詳細ページ表示。4.1 の区別通り)。

## 5. データの集め方の見通し

サービスの中心である「程度・実測」は 1 人では埋めにくいが、次の組み合わせで
集め切れる見通し(近郊 5 件を試しに集めて確認済み)。

- web の公開情報から AI で下書きを作る。人気のキャンプ場は基本情報も程度・実測もほぼ埋まる
- web に情報が無い無名のキャンプ場の程度・実測は、電話・現地で埋める
- 後の段階でユーザー投稿(構造化)で補完・更新する

30〜50 件なら週末 1〜2 回分の作業量。
