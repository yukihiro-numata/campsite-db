# コンセプトドキュメント

最終更新: 2026-07-11

## 1. 目的

趣味で長く育てられる Web サービスを個人開発する。

- 個人開発として継続できる規模で運営する
- 新しい技術を学びながら開発する
- GitHub で公開し、ポートフォリオとして通用する品質を目指す

AI を前提とした**プロダクト**にはしない(チャットで「おすすめを教えて」
のような AI 表面は作らない)。プロダクトの芯は構造化検索・地図・比較。
プロダクト設計・検索・地図・データモデリング・インフラを重視する。

ただし **AI を「データ収集の裏方ツール」として使うことは前提と矛盾しない**。
web 上に散在する実地情報をクロール・抽出して DB を埋める用途は、
プロダクト表面ではなくビルド時の道具であり、上記方針の範囲内とする(6 節)。

## 2. 課題仮説(競合・ペイン調査で検証済み / 2026-07-11)

### 修正後の仮説(確定)

キャンプ初心者が本当に比較したい「行ってみないと分からない情報」のうち、
**"有無・種類"レベルは既存サービスで構造化されつつある。空白なのは
"程度・定性・実測"の情報**(地面の硬さ、トイレのきれいさ、混雑度の実測、
静かさの度合い、サイトの実寸、所要時間での絞り込み)である。これらは
ブログ・YouTube・口コミに散在し、横断比較できない。

→ **"行ってみないと分からない程度・実測情報"を比較可能な軸に構造化**
できれば差別化できる。当初の「スペックが無いから作る」は誤りで、
「散在する質的情報を構造化・横断比較可能にする」に芯を修正した。

### 検証サマリ

当初仮説を A/B/C に分解して検証した(手法: 競合ライブ調査 + Web上の
ペイン調査)。

| 主張 | 判定 | 要点 |
|---|---|---|
| A. 既存は予約・口コミ中心でスペック非構造化 | **半分は誤り** | hinata スポットが地面の種類・24時間管理・近隣コンビニ/スーパー・車乗り入れ・穴場までタグ構造化し掛け合わせ絞込も可能。ただし予約主軸のなっぷは薄く、TAKIBI は予約撤退(2024/9末) |
| B. 実地情報がブログ・YouTube に散在 | **限定的に成立** | 「有無・種類」は構造化済み。散在するのは「程度・定性・実測」情報 |
| C. 初心者の痛みが実在し情報探しに時間がかかる | **概ね成立(中〜強)** | 地面・騒音・トイレ・広さ・買い出しで失敗談/回避策が多層的に存在。「ブログ/YouTube を漁る」が選び方の王道として指南され、集約する二次サービスまで出現 |

### 競合の構造化状況

| サービス | 主目的 | 構造化済み(=差別化にならない) |
|---|---|---|
| なっぷ | 予約 + 検索(最大級) | エリア/料金/予約可否/サイトタイプ/電源/風呂/ペット/様式トイレ。サイト広さは「100㎡以上」の二値特集どまり |
| hinata スポット | 検索(メディア起点) | 上記に加え **地面の種類/24時間管理/近隣コンビニ・スーパー/車乗り入れ/穴場** までタグ構造化 |
| TAKIBI | 情報メディアのみ(予約は 2024/9 終了) | 予約・検索の競合としては実質消滅 |
| Google マップ | 地図 + 口コミ | 実地スペックは非構造化。ユーザーが口コミ件数から混雑度を自力推定 |

### 空白地帯(どこにも構造化されていない = 差別化余地)

1. 地面の"質"(ペグの刺さりやすさ・硬さ・水はけ) ※種類は hinata が構造化済
2. サイトの実寸(㎡)での範囲検索
3. トイレの"きれいさ"(様式は構造化済だが清潔感はない)
4. 混雑度の実測(時期別・実データ)
5. 静かさの"度合い"(穴場の二値のみ)
6. 都心/主要都市からの所要時間での絞り込み

### 判定

**Pivot ではなく「仮説を修正して Go」。** 課題は実在するが、差別化の芯は
「スペックが無い」ではなく「程度・実測情報が構造化されていない」に修正。
ただし後述の最大リスク(11 節)を直視することが Go の条件。

## 2.5 競合の全体像と勝ち筋(2026-07-11 調査)

hinata や既存の集約サービスが、これだけのニーズがあるのに「決定版」に
なれていない理由を掘り、勝ち筋を言語化した。

### なぜ誰も決定版になれていないか(共通の失敗パターン)

1. **単一軸の袋小路**(トイレなう=トイレだけ / キャンプイズム=動画だけ):
   深いが狭く「まず候補を絞る」入口を取れず、横断比較もできない
2. **一次データを持たない集約は無力**(WOM CAMP=他人ブログへのリンク集):
   Google・大手メディアに埋もれ指名検索されない
3. **B2B 掲載課金モデルの構造矛盾**(キャンプイズム=施設が制作費負担):
   払った施設しか載らず網羅不能、かつ利益相反でネガ実測が載らない
4. **鮮度維持コストで失速**: トイレ・地面・電波は変化が速く供給が止まると陳腐化
5. **薄いカバー率でのローンチ**: 数百件では「載ってない」体験が定番化を殺す
6. **市場は淘汰局面**: 予約特化の TAKIBI ですら 2024/9 撤退

なっぷ(約5,900件)も hinata(約7,000件)も、網羅で勝つ代わりに「程度・実測」を
犠牲にしている。ここが空白。

### 核心の再評価: 中立性は「堀」ではなく「優位」(2026-07-11 裏取りで格下げ)

当初「送客・掲載課金で稼ぐ強者はネガ実測を構造化公開できない＝資本で
潰せない堀」と考えたが、仮説検証の結果**この因果は普遍法則としては棄却**
された(裏取りログ: `docs/experiments/2026-07-11-hypothesis-verification.md`)。

- **前提は成立**: 各社は施設課金/送客で稼ぐ(なっぷ 送客手数料 5〜7%、
  hinata OTA送客、キャンプイズム 掲載課金)。掲載施設＝課金顧客は事実。
- **因果は反証される**: **Hipcamp(米)はホストから 10〜15% 手数料を取る
  送客モデルなのに 👍😐👎 の構造化評価と騒音・清潔さのネガを公開**。なっぷ
  自身も多軸星評価＋低評価口コミを掲載。抑制の直接証跡は弱い。
- **生き残る事実**: 「静かさ/混雑/電波/トイレ汚れ 等のネガ方向の実測
  メトリクスを、比較可能な独立軸として持つ社が国内に無い」ことは事実(空白は
  本物)。だがその原因が収益構造とは証明できず、"やれば大手でもできる"。

→ 我々の優位は**「不可侵の堀」ではなく、(a)実在する未充足の空白 + (b)大手の
優先順位が網羅・送客・EC にあり手が回っていない + (c)実測データの収集が
高コスト・主観的(自前実証済み) + (d)非施設課金ゆえのバイアスの無さ**、という
**実行・focus 上の優位**。趣味・ポートフォリオ目的(1 節)では防御可能性は
必須でなく、これで十分。ただし Hipcamp 的な資本が本気で参入すれば追随され
うる前提は持つ。

補足(前向きな裏取り): Hipcamp / The Dyrt / マンションノート(住まいの構造化
ネガ口コミ)は「構造化ネガ比較は商業的に成立する」実例。とくに The Dyrt・
マンションノートは**レビュー対象が非課金(消費者課金/広告)**モデルで、我々の
非施設課金方針(D8 / 7 節)と方向性が一致する。

### 勝ち筋(一言)

> 予約送客・掲載課金に依存しない**中立**の立場で、キャンプ場の「程度・
> 実測情報」(地面の硬さ・静かさ・混雑・電波・傾斜・実寸…)を**横断比較**
> できるようにする。**ネガ情報が載ることこそ資産**。全国を薄く狙わず、
> まず特定エリア/ペルソナで「その界隈の第一想起」を取る。

補強方針:
- 差別化の核は**「主観★」でなく「方法論のある実測指標」**(多軸★だけなら
  hinata が低コストで追随可能。実測まで踏み込めば網羅モデルと相性が悪く
  追随しにくい)
- **体験(モバイル UX)は差別化の主軸ではなく衛生要因**(2026-07-11 裏取り)。
  操作性ペインは実在するが小さく、本丸の不満は予約取得難・鮮度・信頼。
  hinata/sotoshiru/なっぷは既にネイティブアプリを保有し概ね「使いやすい」
  評価。→ UX 単体では戦わず、**「他にない軸(程度・実測・中立)で絞り込める
  × サッと使える」のセットで入口のくさび**にとどめる(→ 4 節・8 節 / D9)
- **鮮度を一級市民に**(各データに「最終実測日」。一括更新に弱い大手の逆を突く)
- カバーは**"軸 × エリア"の縦切り**(薄いカバー率ローンチの罠を回避)

### 避けるべき罠

単一軸に閉じる / B2B 掲載課金に寄せ中立性を捨てる / リンク集に堕す /
鮮度設計を怠る / 薄いカバーで全国に広げる。

### 新規リスク

- **sotoshiru(スペースキー運営)が未調査**。写真+UGC レビュー+スポットの
  アプリで構造が我々に近く、hinata より警戒すべき可能性(11 節)
- **市場の淘汰局面**。ただし 1 節の通り趣味・ポートフォリオ目的のため
  「事業存続」のバーは低く、致命傷ではない

## 4. MVP スコープ(案)

### 入口

条件検索。絞り込み軸は 3〜5 個の少数精鋭で始める(軸が多いほど
1 件あたりの調査コストと実装が膨らむため)。

### 画面構成(最小)

1. 検索ページ(絞り込み + 一覧)
2. キャンプ場詳細ページ(スペック表 + 地図)

### 体験原則

**Web/PWA でモバイルに軽く速く**(D9)。ただしモバイル操作性は差別化の
主軸ではなく**衛生要因**(2026-07-11 裏取り): 操作性ペインは実在するが小さく、
本丸の不満は予約取得難・鮮度・信頼。hinata/sotoshiru/なっぷは既にネイティブ
アプリを持ち概ね「使いやすい」評価 → **"アプリの有無/出来"では戦わない**。
UX は「他にない軸(程度・実測・中立)で絞り込める × サッと使える」のセットで
入口のくさびにとどめ、ネイティブアプリは作らない(8 節)。

### やらないこと(MVP では)

- 予約機能・料金比較
- 自由記述レビュー(比較を壊す断片が増えるため恒久的にやらない)
- ユーザー投稿インフラ(認証・フォーム・モデレーション)。無人の初期は
  無意味なため MVP では作らない。ただし構造化 UGC を後段で開けるよう、
  データモデルには最初から投稿を載せられる余地を残す(D7 / 6 節)
- レコメンド、横並び比較 UI
- 全国網羅

## 5. 収集項目と絞り込み軸

**「収集項目」と「絞り込み軸」は別物**。収集項目は各キャンプ場について DB に
持つ全情報で広い。絞り込み軸(5.2)はそのうち検索で絞れるようにする少数精鋭で
狭い。例: 住所や料金は「収集するが絞り込み軸にはしない(詳細ページに表示する
だけ)」。両者を混同すると「絞り込み軸=集める情報の全部」と誤解する。

### 5.1 収集項目(各キャンプ場について DB に持つ情報)

差別化になる情報(下表③)だけでなく、**名称・住所などの当たり前品質(①)も
必須**。当初 doc は検索・差別化軸しか定義しておらず基本情報が抜けていたため、
ここで 4 カテゴリとして明文化する。

| カテゴリ | 例 | 位置づけ |
|---|---|---|
| ① 基本情報(当たり前品質・必須) | 名称 / 住所 / 緯度経度 / 電話 / 公式URL / 営業期間・シーズン / 定休日 / IN・OUT 時刻 / 予約方法 / 料金レンジ | **MVP 必須**。地図・詳細ページの土台。無いと MVP が成立しない |
| ② 設備・サービス(有無中心) | サイトタイプ(区画/フリー/オート/コテージ) / AC 電源 / 風呂・シャワー・温泉 / 売店・レンタル / ゴミ捨て / ペット可 / 直火 / トイレ様式 / 近隣コンビニ・スーパー・風呂 | 競合も構造化済。差別化にはならないが"当たり前品質"として必要 |
| ③ 差別化・実測(ペインの空白地帯) | 地面の質(硬さ・水はけ) / サイト実寸㎡ / トイレのきれいさ / 静かさの度合い / 混雑度 / 車横付け / 都心からの所要時間 | 2 節の空白地帯。サービスの芯 |
| ④ メタ情報(各項目に付随) | 出典種別(キュレーション/AI/ユーザー) / 出典URL / 確認日 / 報告件数 | 6 節データ戦略と対応。鮮度・信頼性の担保 |

各カテゴリの「埋まりやすさ」は大きく異なる(6 節「埋まり方の 3 層」で実証)。

### 5.2 絞り込み軸(②③ から少数精鋭で選抜)

初心者ターゲットのため「安心系」を主軸に、競合にない「差別化軸」を
1〜2 個混ぜる構成を提案する。3〜5 個の少数精鋭で始める。

| 分類 | 候補 | 備考 |
|---|---|---|
| 安心系(主軸) | トイレのきれいさ / 売店・レンタル有無 / 管理人常駐 / 近隣の風呂・コンビニ | 初心者の最重要関心事 |
| 差別化軸(1〜2 個) | 車横付け可否 / 地面の種類(ペグの刺さりやすさ) / 静かさ | 競合が構造化していない情報 |
| アクセス系 | 都心からの所要時間 | 検索条件として汎用性が高い |

→ データ収集フォーマット作成時に確定する。

## 6. データ戦略

差別化の芯である「程度・定性・実測」情報(地面の硬さ・トイレのきれいさ・
静かさ・混雑度)は、1 人の手動収集では埋めにくい。これを **AI シード →
構造化 UGC で補完** の 3 層で解く。

### 3 層構造

1. **AI シード層**: web 上に散在する情報をクロール+抽出し、DB を"下書き"で
   埋める。クロール可能な軸(所要時間・地面の種類・トイレ様式・実寸)は
   一気に、主観軸(きれいさ・静かさ・混雑)も"暫定値+出典"で埋める。
   → 空欄を減らし、次段の投稿ハードルを下げる
2. **ユーザー確認・修正層(後段)**: 訪問者が「合ってる/違う」をワンタップで
   補正。0 からの空欄記入ではなく確認・修正にすることで投稿が集まりやすく、
   主観軸を実体験で上書きして鮮度・実測を担保する
3. **集約・モデレーション層**: 複数報告を集約(平均化)、出典・確認日・報告
   件数を保持。スパム/荒らしへの簡易対策

### 軸ごとの収集難易度(2 節の空白地帯より)

| 収集しやすさ | 軸 | 主な担い手 |
|---|---|---|
| 易(機械的) | 所要時間 | AI/地図 API |
| 中(公式・ブログにあれば) | サイト実寸・地面の種類・トイレ様式 | AI シード |
| 難(主観・鮮度) | トイレのきれいさ・静かさの度合い・混雑度の実測 | AI 暫定 → UGC で上書き |

無名サイト(web 上に情報が乏しく訪問者も少ない)は AI・UGC どちらでも
埋まりにくい。ここは自分の補正 or 実地訪問でカバーし、UGC は"更新・補完"
担当と割り切る。

### 埋まり方の 3 層(2026-07-11 実証で確認)

人気サイト(氷川キャンプ場)と無名サイト(小沢山荘)の 2 件を実際に AI で
web 集約した結果、**"埋まり方"はサイトの web 露出量で層ごとに断絶する**
ことが分かった(実証ログ: `docs/experiments/2026-07-11-ai-seed-crawl.md`)。

| 層 | 中身(≒5.1 のカテゴリ) | 支えるもの | 無名でも埋まるか |
|---|---|---|---|
| ① レジストリ層 | 名称・住所・電話・大まかな営業期間 | 自治体・地図・電話帳インフラ | ○ 埋まる(無名でも 8〜9 割) |
| ② 運用情報層 | 料金・予約・IN/OUT・定休・公式URL | 施設自身の公式サイト | △ 公式サイト有無で明暗(無名=落ちる) |
| ③ 体験層(=差別化軸) | 地面・実寸・トイレのきれいさ・静かさ・混雑 | 訪問者の UGC(ブログ・口コミ) | ✕ UGC ゼロなら全滅 |
| (例外) 所要時間 | — | 緯度経度から演繹 | ○ 常に埋まる(施設固有でない) |

実証の数値: 人気=基本情報 10/10・6 軸 5.5/6・出典 100%。無名=基本情報
約 4.5/10・6 軸ほぼ 0(所要時間のみ)。**AI 集約は「既に公開された情報の
再集約」であり、無から一次観測は生めない**。訪問者ゼロの無名施設では
差別化の芯(③)が原理的に空白になる。

### AI シードの実効性と含意(実証)

- **有効性は確認できた(下限値として心強い)**: 本文フェッチが不可
  (検索スニペットのみ)という悪条件でも、人気サイトは基本 10/10 + 6 軸
  5.5/6 まで埋まった。本文フェッチが効く本番なら確認日・緯度経度も取れて
  さらに上がる
- **コールドスタートの本丸は無名サイト**: 差別化軸だけは AI で埋まらず、
  電話取材・現地訪問という**非 Web 入力が必須**。AI の役割は「何が空いて
  いるかの可視化 + 電話導線を残す」まで
- 設計への裏取り済み含意:
  1. 各項目に**出典種別・確認日**を持たせ、**空欄は正直に「未確認」表示**
     (無名は空欄だらけになる前提)
  2. 主観軸は**単一の断定値でなく「レンジ + 出典 + 場所注記」**で持つ
     (氷川で地面の硬さがソース間で矛盾した実例)
  3. 収集パイプラインは**本文フェッチ可能なクロール経路**が要る
     (スニペット孫引きでは鮮度=確認日が付かない)

### 原則

- **出典と確認日を項目ごとに記録**し鮮度を担保。各項目は出典種別
  (キュレーション/AI/ユーザー)・確認日・報告件数を持てるデータモデルにする
- **seed then crowdsource**: 投稿インフラはコールドスタート下では無意味。
  初期 30〜50 件は自分で埋め切って「エリア最強」を作り、価値と流入を
  作ってから投稿を開く(D7 / 4 節)
- 蓄積された「構造化された実測 UGC」は競合(hinata でもレビューしか無い)が
  持たない、時間が効く本当のモートになる
- 情報源: 公式サイト、自治体・観光情報、ブログ・SNS・YouTube、衛星写真、
  実地訪問、および将来のユーザー投稿

### 法務・信頼性の留意

- クロールは事実の集約に留め、他者コンテンツの丸ごと転載は避ける
  (robots/ToS・著作権に配慮)
- LLM 抽出は誤帰属・捏造がありうるため、必ず項目ごとに出典 URL を紐づけ、
  検証可能にする

## 7. 収益化

広告収益を第一候補とする(Google AdSense / Amazon アソシエイト /
楽天アフィリエイト)。将来的にキャンプ用品・予約サービス連携を検討。

**制約(D8 と一体)**: 収益化は**非独占のアフィリエイト送客・広告**に留め、
**施設からの掲載課金は取らない**。掲載課金や特定予約先への送客依存は、
レビュー・比較を施設寄りに歪め「ネガ実測も載る中立性」を損なう(2.5 節)。
中立性は"不可侵の堀"ではないが我々の芯であり、収益と衝突したら中立性を
優先する。The Dyrt・マンションノート(非施設課金)が中立比較の成立例(裏取り)。

## 8. 技術方針

| レイヤ | 選定 | 状態 |
|---|---|---|
| フロントエンド | Next.js (App Router)。SEO 重視 + **PWA(モバイルファースト。ネイティブアプリは作らない)** | 候補 |
| バックエンド | Ruby on Rails API | 候補 |
| DB | PostgreSQL + PostGIS | 候補 |
| 地図 | MapLibre + OpenStreetMap(Google Maps 非依存) | 候補 |
| ストレージ | S3 互換(Cloudflare R2) | 候補 |
| インフラ | Vercel / Fly.io / Supabase | 候補 |

方針: **PWA + Web** を主軸とする(D9)。ネイティブアプリは作らない。理由:
(1) なっぷ・hinata・sotoshiru が既にネイティブアプリを保有し概ね好評＝
アプリ空白は無い、(2) 操作性は衛生要因で差別化にならない、(3) ネイティブは
SEO(広告収益の生命線)に乗らない。Web は SEO とモバイル体験を両立でき、
PWA でホーム画面追加・オフライン閲覧などアプリ的な使い勝手も足せる。

実装開始時に ADR として確定させる。
