# コンセプトドキュメント

## 1. 目的

### 主目的

他サービスでは足りないこと・できないことをやり、キャンプ場をより簡単に、
便利に探せるようにする。

### 副目的

1. **ポートフォリオにする**。そのうえで、簡単かつ持続的に開発できる構成を目指す
2. **使いやすくモダンなデザインにする**。既存サービスの UI/UX に不満があるため

## 2. 課題仮説

### 仮説

キャンパーが比較したい「行ってみないと分からない情報」は、既存サービスでの
扱われ方で 2 つに分かれる。

- **有るか・どんな種類か(以下「有無・種類」)**: 例——トイレは有るか/水洗か、
  地面は砂利か芝か、オートサイトか、近くにコンビニがあるか。Yes/No や
  カテゴリで表せるため、hinata などが既にタグ化している。
- **どれくらいか(以下「程度・実測」)**: 例——トイレのきれいさ、地面の硬さ
  (ペグの刺さりやすさ)、静かさ、混み具合、区画の広さ(㎡)。量や度合いの情報で、
  ブログ・YouTube・口コミに散らばって横断比較できない。ここが空白。

→ この**「程度・実測」を比較できる軸に構造化**すれば、行く前に比べて選べるように
なり、キャンプ場探しが楽になる。

### 根拠1: 競合は「有無・種類」止まり

| サービス | 主目的 | 構造化済み(=他サービスでも探せる) |
|---|---|---|
| なっぷ | 予約 + 検索(最大級) | エリア/料金/予約可否/サイトタイプ/電源/風呂/ペット/様式トイレ。サイト広さは「100㎡以上」の二値どまり |
| hinata スポット | 検索(メディア起点) | 上記に加え **地面の種類/24時間管理/近隣コンビニ・スーパー/車乗り入れ/穴場** までタグ構造化 |
| TAKIBI | 情報メディアのみ(予約は 2024/9 終了) | 予約・検索の競合としては実質消滅 |
| Google マップ | 地図 + 口コミ | 実地スペックは非構造化。ユーザーが口コミ件数から混雑度を自力推定 |

最も進んだ hinata でも「有無・種類」のタグ止まりで、「程度・実測」を軸に持つ
社は無い。

### 根拠2: ペインは実在

地面・騒音・トイレ・広さ・買い出しで失敗談や回避策が多層的に見つかる。
「ブログ/YouTube を漁る」が選び方の王道として指南され、それを集約する二次
サービス(トイレ専用 DB・動画レビュー等)まで生まれている。

### 空白地帯(どこにも構造化されていない = 他サービスではできないこと)

1. 地面の"質"(ペグの刺さりやすさ・硬さ・水はけ) ※種類は hinata が構造化済
2. サイトの実寸(㎡)での範囲検索
3. トイレの"きれいさ"(様式は構造化済だが清潔感はない)
4. 混雑度の実測(時期別・実データ)
5. 静かさの"度合い"(穴場の二値のみ)
6. 都心/主要都市からの所要時間での絞り込み

## 2.5 競合の全体像と勝ち筋

hinata や既存の集約サービスが、これだけのニーズがあるのに「決定版」に
なれていない理由と、そこから見える勝ち筋。

### なぜ誰も決定版になれていないか(共通の失敗パターン)

1. **単一軸の袋小路**(トイレなう=トイレだけ / キャンプイズム=動画だけ):
   深いが狭く「まず候補を絞る」入口を取れず、横断比較もできない
2. **一次データを持たない集約は無力**(WOM CAMP=他人ブログへのリンク集):
   Google・大手メディアに埋もれ、名前で探してもらえない
3. **B2B 掲載課金モデルの構造矛盾**(キャンプイズム=施設が制作費負担):
   払った施設しか載らず網羅不能、かつ利益相反でネガ実測が載らない
4. **鮮度維持コストで失速**: トイレ・地面・電波は変化が速く供給が止まると陳腐化
5. **薄いカバー率でのローンチ**: 数百件では「載ってない」体験が定番化を殺す
6. **市場は淘汰局面**: 予約特化の TAKIBI ですら 2024/9 撤退

なっぷ(約5,900件)も hinata(約7,000件)も、網羅で勝つ代わりに「程度・実測」を
犠牲にしている。ここが空白。

### 中立性は強みだが、参入障壁ではない

我々の立場は「予約送客や施設からの掲載課金に依存しない中立」。ただしこれは
他社が真似できない壁ではない。送客で稼ぐ Hipcamp(米)も、ホスト手数料を
取りながら 👍😐👎 の評価や騒音・清潔さのネガ情報を構造化して公開しているし、
なっぷ自身も多軸の星評価と低評価の口コミを載せている。つまり「送客・掲載課金で
稼ぐと施設のネガ情報を出せない」わけではなく、大手もやろうと思えばできる。

確かなのは「"程度・実測"(静かさ・混雑・電波・トイレの汚れ 等)を比較できる軸で
持つ国内サービスが今は無い」こと。だから我々の強みは"壁"ではなく、次の 4 つ:

- (a) 実在する空白がまだ埋まっていない
- (b) 大手は網羅・送客・EC に注力していて、程度・実測まで手が回っていない
- (c) 実測データは集めるのが高コストで主観的(自分で試して確認済み)
- (d) 施設からお金を取らないのでバイアスがない

個人開発(1 節)なら、真似されない完全な守りは要らず、これで十分。ただし
Hipcamp のような資本が本気で参入すれば追いつかれうる。なお「施設からお金を
取らない」方針は、同じく非課金で運営する The Dyrt やマンションノートが
「ネガ情報も含む構造化比較が事業として成立する」実例として裏づける(D7)。

### 勝ち筋(一言)

> 予約送客・掲載課金に依存しない**中立**の立場で、キャンプ場の「程度・
> 実測情報」(地面の硬さ・静かさ・混雑・電波・傾斜・実寸…)を**横断比較**
> できるようにする。**ネガ情報が載ることこそ資産**。全国を薄く狙わず、
> まず特定エリア/ペルソナに絞り、そこで一番に思い出される存在になる。

補強方針:
- **主観の星評価ではなく、決まった手順で測った実測値で持つ**。多軸の星評価
  だけなら hinata も安く真似できるが、実測(同じ手順で測れる値)まで踏み込めば、
  網羅を優先する大手には手間がかかり追随しにくい。
- **UI/UX は競合との一番の違いにはしないが、使いやすくモダンにすることは目指す**
  (副目的②)。一番の違いはあくまで「他にない軸で絞り込めること」。詳細は mvp.md。
- **データの鮮度を最優先にする**。各データに「最終実測日」を持たせる。大手は
  データを一括でしか更新できず古くなりやすいので、そこで差をつける。
- **範囲を欲張らず、軸とエリアを絞る**。中途半端なカバー率で公開すると
  「載っていない」体験が増えて定番になれない。

### 残るリスク

- **大手が程度・実測の比較に乗り出す**: hinata も スペースキー(なっぷ + ソトシル)
  も、現状は「有無・種類 + 写真 + 自由記述レビュー」で我々の空白を埋めていない
  (調査済み)。ただし多軸★の追加は
  低コストで真似でき、彼らは規模・データを持つ。防御は、主観★でなく実測
  (決まった手順で測った値)まで踏み込むことと、中立性(施設から課金しない＝
  彼らが取りにくい)。
- **市場の淘汰局面**。ただし個人開発(1 節)なら事業存続のハードルは低く、
  致命傷ではない。

## 4. 収集項目と絞り込み軸

**「収集項目」と「絞り込み軸」は別物**。収集項目は各キャンプ場について DB に
持つ全情報で広い。絞り込み軸(4.2)はそのうち検索で絞れるようにする少数精鋭で
狭い。例: 住所や料金は「収集するが絞り込み軸にはしない(詳細ページに表示する
だけ)」。両者を混同すると「絞り込み軸=集める情報の全部」と誤解する。

### 4.1 収集項目(各キャンプ場について DB に持つ情報)

他サービスで探せない情報(下表③)だけでなく、**名称・住所などの当たり前品質(①)も
必須**。収集項目は 4 カテゴリに分ける。

| カテゴリ | 例 | 位置づけ |
|---|---|---|
| ① 基本情報(当たり前品質・必須) | 名称 / 住所 / 緯度経度 / 電話 / 公式URL / 営業期間・シーズン / 定休日 / IN・OUT 時刻 / **予約要否・予約方法** / 料金レンジ | **MVP 必須**。地図・詳細ページの土台。無いと MVP が成立しない |
| ② 設備・サービス(有無中心) | サイトタイプ(区画/フリー/オート/コテージ) / AC 電源 / 風呂・シャワー・温泉 / 売店・レンタル / ゴミ捨て / **ペット可** / **直火・川遊び可否** / トイレ様式 / 近隣コンビニ・スーパー・風呂 | 他サービスでも探せるが、"当たり前品質"として必要 |
| ③ 程度・実測(ペインの空白地帯) | 地面の質(硬さ・水はけ) / サイト実寸㎡ / トイレのきれいさ / 静かさの度合い / 混雑度 / 車横付け / 都心からの所要時間 | 2 節の空白地帯。サービスの芯 |
| ④ メタ情報(各項目に付随) | 出典種別(キュレーション/AI/ユーザー) / 出典URL / 確認日 / **裏取り本数** / 確信度 | 鮮度・信頼性の担保 |

各カテゴリの「埋まりやすさ」は大きく異なる(5 節)。運用ルール:

- **緯度経度は「収集」でなく住所からの自動生成(ジオコーディング)**列に分類。
- **「実測」種別は web フェーズでは常に空欄**になるため現地調査フェーズ専用。
- 品質指標は「充足率」でなく **「裏取り本数(確信度)」**とする(5 軸は 1 本の
  ブログでもセルが埋まるため)。

### 4.2 絞り込み軸(②③ から選抜した 5 軸)

「ターゲット(初心者〜中級者)に刺さる × 他サービスで探せない × 埋められる」で 5 軸を選抜。

| # | 軸 | 分類 | 埋め手 |
|---|---|---|---|
| 1 | 都心からの所要時間 | アクセス | AI/地図(易) |
| 2 | 車横付け(オートサイト)可否 | 安心・有無 | AI(易) |
| 3 | トイレのきれいさ | 程度・実測 | **web=参考 / 現地=確定** |
| 4 | 地面の種類 + 硬さ(ペグ) | 程度・実測 | 種類=AI / 硬さは **web=参考 / 現地=確定** |
| 5 | 静かさ・混雑(穴場度) | 程度・実測 | UGC/AI 暫定 |

- 売店・レンタル・風呂・近隣コンビニ等は**収集はするが絞り込み軸にはしない**
  (詳細ページ表示。4.1 の区別通り)。

## 5. データの集め方の見通し

サービスの芯である「程度・実測」は 1 人では埋めにくいが、次の組み合わせで
集め切れる見通し(近郊 5 件を試しに集めて確認済み)。

- web の公開情報から AI で下書きを作る。人気サイトは基本情報も程度・実測もほぼ埋まる
- web に情報が無い無名サイトの程度・実測は、電話・現地で埋める
- 後の段階でユーザー投稿(構造化)で補完・更新する

30〜50 件なら週末 1〜2 回分の作業量。
