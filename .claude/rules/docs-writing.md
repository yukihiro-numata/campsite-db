# docs/ ドキュメント作成ルール

`docs/` 配下のドキュメント(概念設計・仕様・決定記録など)を書く・直すときは、
次の 2 点を守る。実証ログ(`docs/experiments/`)は「経緯の記録」が目的なので、
ルール 1 の対象外とする。

## 1. 結論ファーストで、冗長な経緯を書かない

- 各項目は**結論を先に、簡潔に**書く。「いつ・何を考え直したか」の履歴は
  本文に残さない。
- **例外(残す)**: 経緯が結論の理由になっている場合は残す。
  例:「当初 X と考えたが、証拠 Y で反証されたので Z に修正」。
  証拠 → 結論の表(検証サマリなど)も、結論を支える根拠なので残す。
- 決定・仮説が変わったら、**本文は結論を上書きする**。変更履歴は git と
  実証ログに任せ、本文に取り消し線の履歴を溜めない。
- 未決事項の類は「**まだ開いているもの**」だけ載せる。済んだ項目は該当節に
  反映して消す。
- 同じ結論・数値を複数の節で繰り返さない。1 か所を正典にし、他は参照する。

## 2. 平易な単語を使う(読者はエンジニア / IT の人)

- 基準は「**働くエンジニアに一般的か**」。一般人向けではない。
- **残してよい(IT 一般語)**: MVP, SEO, PWA, API, ADR, UGC, EC, B2B,
  ペルソナ, ピボット, コールドスタート, メトリクス, パイプライン,
  ジオコーディング など。
- **避ける**:
  - 和文に生埋めの英単語(例: focus → 「注力」)
  - 定訳のない英語フレーズ(例: seed then crowdsource →
    「まず自分で埋め、後から投稿で補う」)
  - 文学的比喩・IT 外のジャーゴン(例: くさび → 「取っかかり」、
    一級市民 → 「最重要項目として扱う」、モート → 「堀」に統一)
- 専門用語をあえて残す場合は、**初出に一言の注**を付ける
  (例: 衛生要因(あって当たり前で、良くても差別化にならない要素))。
